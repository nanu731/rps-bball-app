## Next native verification task

When implementation resumes, diagnose the previous input failure before assigning
it to the app or tools. Use a bounded XCUITest pilot as an alternative mechanism:
launch, navigate, type, save, reopen and assert visible persistence with screenshots
and failure hierarchy. Use the isolated test app/container, disposable synthetic
records and accounts, and a privately verified preservation baseline. Protect
original records and personal Xcode working bytes/staged entries; no app uninstall,
container reset or deletion is an automation recovery strategy.

A passing pilot establishes only the exercised path. Expand to both device
families, appearance, Dynamic Type, keyboard, permissions and recovery. A failed
pilot needs a recorded hypothesis, diagnostic evidence and next experiment; it
does not automatically clear or implicate the app. Hand back only a demonstrated
human-only gate, and continue other authorized work.

Visual acceptance needs fresh Simulator captures and inspection. UX acceptance
needs actual journeys and state transitions. Performance acceptance needs measured
startup, loading, transfer and interaction behavior; no invented latency targets
or success claims. Cover initial startup, pending requests, empty/denied/error,
Retry/cancellation, duplicate taps, offline retained clips and safe draft recovery.
Tie progress feedback to actual operations rather than decorative delay.

Use bounded audit/fix/confirmation passes. Source checks, screenshots, interaction
tests, hosted integration and physical-device evidence remain separate. Credentials,
MFA/unlock, authentic sample content, unavailable hardware and separately approved
release may still need the owner; downloaded skills cannot supply them.
